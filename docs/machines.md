# Machines: one repo, many environments

The same clone runs on an AWS GPU box, a MacBook, a Linux workstation and a CI runner. They differ in what is fast, what is durable, what is shared and what tools behave like. YBase keeps those differences out of the rules and the lessons by putting them in four tiers:

| Tier | File | Committed? | Holds |
|---|---|---|---|
| **Profile** | `profiles/<type>/profile.sh` and `NOTES.md` | yes | defaults and lessons true of every machine of a type |
| **Machine facts** | `.ybase/MACHINE.md` | no, generated by `ybase doctor` | what this one machine actually has |
| **Machine settings** | `.env` | no | the pinned profile and the paths only this machine knows |
| **Private terms** | `deny.list` in each knowledge base | no | terms the leak check must refuse |

## Which profile applies

First match wins:

1. `YBASE_PROFILE=<name>` in the environment.
2. `YBASE_PROFILE` in `.env`, written by `ybase profile <name>` and removed by `ybase profile --unpin`.
3. Auto-detection, which reads only local files: a CI job (`CI` is `true` or `1`) is `ci`; otherwise `Darwin` is `macos`; Linux whose DMI vendor, board asset tag or hypervisor UUID identifies EC2 is `aws`; any other Linux is `linux`.

When setup auto-detects `ci`, it prints a line saying so and that `ybase profile <name>` pins another profile. `YB_CI` replaces `CI` for detection, as `YB_UNAME` replaces `uname` in tests; an empty `YB_CI` means "not CI" even when `CI=true`. A pinned profile always beats CI detection.

`ybase profile` prints the profile in force and where it came from.

## The `.env` file

`.env` at the repo root holds this machine's settings. It is gitignored, parsed and never sourced. One `KEY=VALUE` per line; the value is everything after the first `=`, taken literally (no quotes, no escapes, no inline comments). Blank lines and lines starting with `#` are ignored. The process environment wins over the file when its value is non-empty. `bin/ybase setup` creates the file with a commented header and writes only keys it can resolve, never rewriting one that is already set unless a flag names it (`--profile`, `--kb`, `--repos-root`); add your own lines freely, they are kept.

| Key | Meaning | Default |
|---|---|---|
| `YBASE_PROFILE` | pinned machine profile | auto-detected |
| `YBASE_SCRATCH` | scratch directory | from the profile |
| `YBASE_WORKTREES` | where worktrees go: a relative name is a folder inside each repo, an absolute path gets one folder per repo | `.worktrees`, or from the profile |
| `YBASE_FAST_DIR` | fast local disk (aws profile) | probed |
| `YBASE_REPOS_ROOT` | where managed repos are cloned | the directory containing YBase |
| `YBASE_REPO_PATH_<KEY>` | one repo's path on this machine | `<repos root>/<name>` |
| `YBASE_KB_PRIMARY` | KB that receives new content | `<YBase>/kb` |
| `YBASE_KB_PATHS` | additional KB roots, separated by `:` | empty |
| `YBASE_GUARD_READONLY_CHECKOUT` | `1` turns on the read-only main checkout guard | off |
| `YBASE_GUARD_PR_DRAFT` | `1` turns on the draft-PR guard | off |
| `YBASE_ALLOW_GATE` | `1` turns on the allow gate, which approves a compound command when every part matches an allow rule; a convenience with known gaps, not a security boundary ([ADR 0003](adr/0003-allow-gate-is-opt-in.md)) | off |
| `YBASE_PUBLIC_REPO` | the public repository `ybase publish` and `absorb` use: a GitHub `owner/name`, or a git URL or path ([publishing](publishing.md)) | unset: both commands refuse |
| `YBASE_LAUNCHER` | `off` stops setup writing the `ybase` command outside the clone ([ADR 0009](adr/0009-a-command-on-the-path.md)) | on, except in the `ci` profile |
| `YBASE_CODEX_DELEGATION` | `off` stops this machine handing work to Codex ([delegation](protocols/delegation.md)) | on when the Codex CLI is installed, else off |

Shell tools read it with `yb_setting KEY` (`tools/lib.sh`); Python tools with `tools/envfile.py`.

## What each profile decides

| | aws | macos | linux | ci |
|---|---|---|---|---|
| Scratch (`TMPDIR`) | instance-store NVMe when present, else repo `tmp/` | repo `tmp/` | repo `tmp/` | `$RUNNER_TEMP/ybase` when set, else repo `tmp/` |
| Scratch durable? | no on NVMe | yes | yes | no |
| Worktrees | on NVMe when present | in each repo's `.worktrees/` | in each repo's `.worktrees/` | in each repo's `.worktrees/` |
| Doctor probes | ephemeral storage, crowded shared `/tmp`, AWS credentials | bash 3.2, case-insensitive filesystem, Apple Silicon | container detection | a note that nothing outside the checkout survives |

Every profile also gets the common probes: git and python3 present (with a warning below Python 3.10), a git `user.email`, `gh` sign-in when `gh` is installed, each KB's state and layout version, repo-local git settings, repository filesystem type (with a warning on a network filesystem), scratch writable, and GPU.

## Setting up a machine

```bash
git clone <repo-url> YBase && cd YBase
bin/ybase setup                 # detect profile, choose the primary knowledge base, create `.env` and the other local files, run doctor
eval "$(ybase env)"         # TMPDIR and YBASE_* for this shell
```

Setup also writes a launcher named `ybase` into `~/.local/bin`, so every later command is `ybase <command>` from any folder. The launcher runs the checkout you stand in, which means a worktree runs its own copy, and otherwise the main checkout that installed it. A worktree has no `.env`, so its copy reads the settings of its main checkout. Three limits:

- If `~/.local/bin` is not on your PATH, setup prints the line to add to your shell profile. It never edits the profile itself. Until then, type `bin/ybase` in the clone.
- Setup never replaces a file named `ybase` that it did not write. It says so and leaves the file.
- The `ci` profile and `YBASE_LAUNCHER=off` install nothing.

The doctor writes the form that works on this machine into `.ybase/MACHINE.md`, as `command:`. If you move the clone, run `bin/ybase setup` in its new place.

Options:

- `--profile <name>` pins a profile.
- `--non-interactive` never reads stdin or asks a question, even when stdin is a terminal. Without `--kb`, an already-set primary knowledge base is kept, else `kb/` in the checkout is initialised. The `ci` profile implies this flag, and the CI workflow runs `bin/ybase setup --non-interactive` before the doctor dry run.
- `--kb <path>` makes that path the primary knowledge base, as `ybase kb primary` does, and skips the question in an interactive run.
- `--repos-root <path>` sets `YBASE_REPOS_ROOT`, replacing a value already there. `--kb` and `--repos-root` each need a value.
- `--parent-importer` writes `../CLAUDE.md` so a Claude Code session started in a sibling directory, such as a code repository next to this one, still loads these rules.

Re-run `ybase doctor` whenever something git-shaped, path-shaped or credential-shaped misbehaves. It is idempotent and prints one `fix:` line per change it makes. It only changes repo-local git settings, the profile's own directories and the three generated files in `.ybase/` (`MACHINE.md`, `KB.md`, `REPOS.md`).

## Adding a machine type

1. `cp -R profiles/_template profiles/<name>` and fill in `profile.sh` and `NOTES.md`.
2. If the type can be recognized from local files, add a branch to `yb_detect_profile` in `tools/profile.sh` and a case to `tests/test_profile.sh`. Otherwise pin it on each such machine with `ybase profile <name>`.
3. Run `ybase doctor --dry-run` on a machine of that type and read the report.

Add a profile when a class of machine needs a different setup, not when one machine has a quirk. A quirk of one machine is a line in its `.env`.

## Hooks

`.claude/hooks/` holds the guards Claude Code runs around its own tool calls, wired in `.claude/settings.json`. The blocking ones refuse a whole-filesystem walk, a `pgrep -f` that matches its own shell, a bare `$VAR` that zsh will not word-split, a `python3` below the project's `requires-python`, a `gh` call that opens a PR for review (the landing convention in [`law/pr.md`](law/pr.md)), a commit or PR text with a leak, and a write into the main checkout; the rest advise or record. Two of the blocking ones are opt-in and ship off: the draft-PR guard (`YBASE_GUARD_PR_DRAFT=1`) and the main-checkout guard (`YBASE_GUARD_READONLY_CHECKOUT=1`). [`architecture.md`](architecture.md) tabulates each hook and its kind. Each hook's docstring says what it refuses, what passes and its escape: an environment variable, set as a prefix on the command (`SCAN_WIDE=1 find /mnt/data ...`) or in the session's environment for a tool with no command line, never a flag.

Claude Code loads `.claude/settings.json` only for a session started inside this clone. To keep five of the blocking guards (the leak guard and the whole-filesystem walk, `pgrep -f`, zsh word-split and draft-PR guards) in a session started elsewhere, such as a managed repo or the folder above your repos, register them once per machine in the user-level settings. The moment rules, the Python floor guard and the file guard are not installed this way: they apply only in a session started in YBase, which is one more reason to start sessions here.

```bash
ybase hooks install-user --dry-run   # show what would change
ybase hooks install-user             # merge into ~/.claude/settings.json (or $CLAUDE_CONFIG_DIR)
ybase hooks install-user --remove    # take them out again
```

Each entry runs the project's own copy of the hook when the session has one and this clone's copy otherwise, so a YBase session never runs a guard twice. The command is idempotent and keeps every other setting in the file. Run it from the clone that will stay on disk: the entries name its hooks by absolute path. `tools/pick_python.sh` is the interpreter picker the Python-floor hook names in its refusal; it works on its own too (`tools/pick_python.sh --for-path .`).

Codex runs one of these hooks, the allow gate, through `.codex/hooks.json`; like in Claude Code, it is off unless `YBASE_ALLOW_GATE=1`. [`codex.md`](codex.md) carries the rules of the others as instructions it holds itself.

## Portability rules for tools

- Shell tools run under bash 3.2 (macOS `/bin/bash`) and under both GNU and BSD userlands: no associative arrays, no `mapfile`, no `sed -i`, no `readlink -f`.
- Python tools use the standard library only.
- The CI workflow runs the tests and the check registry on both Ubuntu and macOS.
